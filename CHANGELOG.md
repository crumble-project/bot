# Changelog

## Unreleased

- Run automations when a webhook arrives, through a [Doorstep](https://github.com/crumble-project/doorstep) event relay, so the server needs no public address. Set the relay URL and the Doorstep account token in **Settings** > **Event relay** (`GET` and `PUT /v1/event-relay`; the token is plugin setting `doorstep:token`, which can come from a password manager), and add event sources there (`GET` and `POST /v1/event-sources`, `DELETE /v1/event-sources/{id}`; the webhook address is returned once; a source in use can't be deleted). In the automation editor, select **Event** under **When** and pick a source; `Schedule.eventSourceId` replaces `cron` and `runAt`, and exactly one of the three is set. The bots' automation tool takes `eventSourceId` and lists sources with action `sources`. A prompt automation's bot receives the prompt followed by the event's method, query, headers, and body (up to 32 KiB of UTF-8 text) marked as untrusted data; the chat shows only the prompt, with `MessageOrigin.kind` `event` and the new `source` field, and intent checks count only the prompt as the owner's request. The new `event_payload` tool pages through longer or binary bodies. Script automations get `CRUMBLE_EVENT_ID`, `CRUMBLE_EVENT_SOURCE`, and `CRUMBLE_EVENT_FILE`. Events are acknowledged after they're stored and deduplicated by ID; an automation handles its events one at a time, oldest first, and a failed hand-off is retried every 30 seconds up to 10 times. Events are kept for 30 days. Provider signatures aren't checked yet.
- Fix the blank web UI in Docker images by keeping the server contract imports available in production installs.
- Connect Discord to existing bot chats with a default bot, leading `@handle` aliases, and replies that select the answering bot. Configure the token, one owner user ID, allowed channels, direct messages, and connection status on its own page, **Settings** > **Message gateways** > **Discord**. Only that owner can submit messages, with bot-chat owner authority. Previous sender allowlists are disabled until an owner is configured. Only answers associated with Discord requests return externally; the original messages and answers stay in the bot transcript. In the web chat, a message sent through Discord shows **Sent from Discord** under it, and `MessageOrigin.via` is `discord`; it keeps owner authority. While the bot works, the channel shows it typing; answers arrive as plain replies without a bot name header. Text only. Retries back off and stop after 10 failures or 24 hours. Completed receipts clear gateway message payloads and retain duplicate detection and reply routing for 30 days, without promising exactly-once delivery.
- Plugin keys, such as the Discord bot token and the Exa API key, can be read from a connected password manager. `PUT /v1/plugin-settings/{pluginId}/{key}` takes `{"reference": {"passwordManager", "reference"}}` instead of `{"value"}`, checked by reading it once; `GET` returns each setting's `passwordManager` and `reference`.
- Compiled-in plugins can contribute chat adapters through `CrumblePlugin.chatAdapters`. Discord is the first adapter; loading third-party adapters without rebuilding remains deferred.

## 0.3.0

- Desktop jobs check each acting call with an intent check before it runs. The account's judge model answers whether the action is irreversible and whether the owner asked for it, from the owner's messages, the job's task, and the action's target, never the page's text. Buttons and links named like Pay, Buy, Order, Send, Delete, or Confirm, and Enter in a form field, always count as irreversible. An irreversible action the judge isn't confident about is held: the bot chat shows a card to approve or decline it, and the job waits. Over the API: `GET /v1/agents/{id}/held-actions` and `POST .../{actionId}/approve` and `.../decline`. Held actions show as `held-action` events in `TranscriptMessage`, with the new `heldAction` field.
- Choose the judge model in **Settings** > **Judge model** or with `GET` and `PUT /v1/judge-model`. The default is GPT-6 Luna through OpenAI Decisions, which needs an OpenAI API key. Without a classifier model, a small chat model such as Claude Haiku 5.5 judges. Each classifier has its own in-intent bar: 50% for Jev, 90% for models not yet evaluated.
- Each intent check's token usage and cost is recorded on its `computer_use` call, so a desktop job's usage includes its judge. Jev is priced at TypeSafe's $0.042 per million input tokens, since pi-ai's catalog lists it at $0.
- Add `bun tools/intent-eval.ts` in `apps/server`: it runs a judge model on 38 labeled desktop actions and reports latency, tokens, cost, and what each in-intent bar would hold. It makes paid calls with the provider's key from the environment, so it runs locally, never in CI.
- The bot's model now sees each owner message and automation's instructions prefixed with `[message <request ID>]`; script automation output is not tagged and never counts as the owner's request, and the `desktop` tool's `start` and `send` take `owner_messages` to cite them. The job keeps those messages verbatim, plus the owner's latest message, for its intent checks; an ID that isn't an owner message of the chat is rejected.
- A desktop job action held for the owner's approval now notifies the owner, on the web and through native push: a `reply` activity event with origin `desktop`, the job's `jobName`, and a preview naming the action.
- Reply events and push payloads gain an optional `waitingFor`: `approval` for a held desktop action, `credential` or `login` when the bot's turn asked for one with `request_credential` or `request_login`.
- Fix web notifications never showing: the **Bot replies** switch looked on before the browser had granted permission, so turning it on never asked. It now shows off until permission is granted. Web notifications carry the Crumble icon.
- The web app plays a sound with each notification, using cuelume: `ready` for replies, `attention` for approvals, and `attention` in the `mech` theme for credential and login requests. Notifications that wait for you stay until dismissed. Hear them at `/ui/sounds`, a page outside the navigation. Turn it off in **Settings** > **General** > **Sound**. The tab title counts unseen replies and names the open chat, such as `(3) Atlas | Crumble`; opening a chat clears its replies from the count.
- The web app draws its own scrollbars with shadcn's ScrollArea on pages, the sidebar, the bot details panel, and editor sheets: a thin bar that shows while you scroll or hover. The chat transcript, menus, and code blocks keep the browser's scrollbar, made thin and in the theme's muted text color.
- Fix a coding or desktop job's activity opening at the top: it now opens at the newest step and follows new steps while the job works, like the bot chat.
- Workspace images ship Bun 1.4.4 (`bun` and `bunx`) instead of Node: the base image is `debian:trixie-slim`. Railway workspaces install Bun too, and keep the Node their Ubuntu comes with. A new image recreates each bot's machine on its next boot: `/workspace` is kept, programs installed outside it are not.
- The installed web app uses the Crumble icon on the home screen instead of the placeholder ring, with a maskable variant for Android.
- Password managers and workspace backends are plugin contributions, like providers and job kinds. Web search provider and password manager IDs come from one list (`shared/vendors.ts`) that the contract, the domain, and the web UI derive from. Nothing changes for owners.
- The API reads the services its routes need from the account instead of the tenant passing each one, and registers routes from one list; store schema files are collected by name. Nothing changes for owners or clients ([ADR 0008](docs/adr/0008-feature-wiring.md)).
- Plugins declare the settings they need, such as the Exa API key. `GET /v1/plugin-settings` lists each plugin's settings and whether each has a value, and `PUT` and `DELETE /v1/plugin-settings/{pluginId}/{key}` set and remove one. **Settings** > **Web search** draws the Exa key from that list and looks the same. `PUT` and `DELETE /v1/web-search/exa-key` still work and are deprecated. A saved Exa key moves to its plugin on upgrade ([ADR 0009](docs/adr/0009-plugin-settings.md)).
- `GET /v1/capabilities` adds `jobKinds`, the kinds of background job bots can be given on this server, such as `coding` and `desktop`.

## 0.2.0

- Fix declining a credential request in **Settings** > **Credentials** deleting the saved credential of the same name, when the bot asked for it on more hosts. Fix a new credential request in the bot chat showing as saved or declined instead of offering its form, when the credentials were loaded just before the bot asked.
- Bots ask for a login with the new `request_login` tool when a desktop job finds a sign-in page no login covers. The request shows as a card in the bot chat and under **Waiting for you** in **Settings** > **Logins**; saving or declining it starts a bot turn with a notice.
- Manage a bot's logins in **Settings** > **Logins**: name, hosts, username, password, and an optional one-time code, each stored in Crumble or read from a password manager, or all from one 1Password item. Each login lists its fills from the last 90 days. Over the API: `GET /v1/agents/{id}/logins`, `PUT` and `DELETE /v1/agents/{id}/logins/{name}`, and `GET /v1/agents/{id}/logins/{name}/uses`. The new **Logins** docs page explains how desktop jobs fill them.
- The credential proxy swaps a credential's placeholder only in request headers, no longer in the URL. A service could log, store, or echo a URL that held the value, so a job could read it back. An API that takes its key only as a query parameter can no longer use a credential. The credentials docs now advise scoping each credential's token to the work the bot does.
- Microsandbox workspaces block outbound UDP except DNS. UDP left the machine past the workspace proxy and the network policy, which only see TCP. Machines made before this are created anew on their next boot: `/workspace` is kept, programs installed outside it are not.
- Bot desktops' Chromium no longer uses QUIC (HTTP/3) or Encrypted ClientHello, so all its traffic goes through the workspace proxy under the real host name. Before, QUIC went out over UDP past the proxy, and on ECH sites such as those behind Cloudflare the network policy and the credential proxy saw only the outer name, such as `cloudflare-ech.com`. Rebuild the desktop image to apply it.
- Desktop jobs work faster on web pages: `computer_use` gains `open` and `read`, which load and read a page in Chromium with its elements as refs, and `click`, `type`, `set_value`, and `scroll` act on a `ref`. `capture` takes a `query` to read only matching elements, and `steps` runs several accessibility actions in one call. In a local test, filling and submitting a form took 2 s instead of 11 s. cua-driver now gets its arguments on stdin instead of a temporary file, and every job on a bot desktop shares one cua-driver session.
- Fix the credential proxy failing about one host certificate in 128 (an OpenSSL `INVALID_INTEGER` error): a random serial number that started with a zero byte wasn't valid DER.
- An MCP server connection that opened while its token or settings changed is closed instead of kept, so the bot's next use connects with the new credentials. The tool call that hit it fails with "MCP server credentials changed; retry this task".
- Document password managers on a new **Password managers** concepts page (connecting, reference formats, cache timings, and what each kind of secret does when it can't be read), and add **Password manager** to the glossary.
- Read a credential's value, a provider's API key, or an MCP server's token from a connected password manager: their editors offer **Crumble** or each connected password manager. A credential whose newest use couldn't read its value shows the error in its row.
- Show provider logos in **Settings** > **Providers** from LobeHub Icons (`@lobehub/icons-static-svg`, MIT), inlined into the web bundle. Radius, TypeSafe, and Melious have no logo there and keep their letter tile.
- Connect 1Password or Bitwarden Secrets Manager in **Settings** > **Password managers**. Each row shows how many secrets read from it, and it can't be disconnected while any do. Adds the `simple-icons` dependency to the web app for their logos.
- Connect 1Password or Bitwarden Secrets Manager over the API with `GET`, `PUT`, and `DELETE /v1/password-managers/{id}`. Connecting signs in once to check the token, and a new token drops values read with the old one. A password manager can't be disconnected while a secret reads from it. Contract 3.4.0.
- Save a bot credential as a password manager reference instead of a value. Saving one reads it once to check it, and a reference that can't be read is rejected without saving anything. Credentials show where their value comes from and why their newest use couldn't read it.
- Save a provider API key as a password manager reference with `PUT /v1/providers/{provider}`. A reference that can't be read is rejected, and the previous key stays.
- Read an MCP server's bearer token from a password manager with `tokenReference` when creating or updating the server. A reference that can't be read is rejected without changing the server. Changing a server's token or reference, including saving a new token in Crumble, now closes its open connection, so the next use signs in with the new one.
- Add `CRUMBLE_MASTER_KEY` to keep a usable encryption key out of the data directory. When it's set, each account's key is stored wrapped in `.secret.key.wrapped`, existing plain `.secret.key` files are wrapped and deleted on start, and the server refuses to start an account whose key the master key can't unwrap. Without it, nothing changes, and the server logs at startup that keys are stored next to the data.
- Bots cite web pages inline. In bot chats and group chats in the web app, links to pages the bot searched or read in that turn show as source chips with the site's name at the end of the message. Group messages from bots carry these pages in the new optional `sources` field of `TranscriptMessage`.
- Choose a default web search provider for the account and override it per bot. Add an Exa API key shared by bots on the account.
- Add web search and page reading through Mixed. New bots created in the web app have **Web search** on by default; owners can turn it off per bot. Existing bots keep their capabilities. Mixed uses free, rate-limited services without an API key.
- Add passkeys: after signing in with a password, add, rename, and remove passkeys in **Settings** > **General**, then sign in with it from the sign-in page or the browser's autofill. Passwords keep working. On a server with no configured address, passkeys use `localhost`, because browsers don't accept an IP address for them, and the server accepts sign-ins from `localhost` as well as `127.0.0.1`.
- Improve the web app on iPhone when installed to the home screen: pages no longer stack an extra header row above their own, the sidebar no longer focuses Search when it opens, the status bar matches the open sidebar, and the message box clears the home indicator.
- Fix emoji reactions being cut off below chat bubbles, and long setting descriptions pushing badges out of their card.
- Show bot request decisions as centered notices in the chat.
- Show newly approved bots in the sidebar without reloading the page.
- Fix Fallow Code Scanning uploads by assigning each SARIF run a distinct category before uploading. PR comments and audit gating remain enabled; fork pull requests skip the upload.

- With code mode on, a bot asks for a credential with a direct tool call again, so the chat shows the request card where the owner enters the value.
- Add bot requests: bots with **Create bots** can propose a new bot, and owners can edit, approve, or decline the proposal in chat.
- Replace credential request links with chat cards where owners can save or decline a credential without leaving the conversation.
- In the web app, messages from tasks, script tasks, credentials, and other bots appear as a centered line you can expand, instead of a bubble that looks like the owner's own message.
- Fix `schedule`, `ask_bot`, `delegate`, `delegation_status`, and `list_bots` in code mode: a successful call returns its result instead of failing with it as the error. The bundled tasks and bot messaging skills call these tools from code mode when it is on, instead of sending the owner to the app.

- Add script tasks: a bot with coding jobs can run a command in its workspace on a schedule, with a configurable timeout and optional results sent to its chat. The Tasks page lists script task runs. Existing script tasks can be converted to prompt tasks without coding jobs or workspaces. Updates validate the complete task before saving; shutdown stops admitting script runs and finalizes runs recorded during shutdown.

- `bun run check` and the pre-commit hook fail when an `AGENTS.md` or `CLAUDE.md` names a path that does not exist. `AGENTS.md` now points at Effect under `apps/server/node_modules/`, where Bun installs it. `bun run --cwd apps/server db:generate` (and `db:generate:push`) generates migrations, and the contributing docs describe it.
- New features no longer start as specifications in `crumble-project/spec`, which is archived. The contributing docs drop the proposal process and the Specifications page, which now redirects to Contributing.
- The canonical glossary moves from `crumble-project/spec` to `GLOSSARY.md` in this repository. The Android and Apple glossaries and the docs site's Glossary page link here.
- Crumble is licensed under the GNU Affero General Public License v3.0 only (`AGPL-3.0-only`). The repository has a `LICENSE` file, each `package.json` has a `license` field, and the published images carry the `org.opencontainers.image.licenses` label. Pull requests still only check and build them.

## 0.1.0

- Publish the server image. `ghcr.io/crumble-project/crumble-server` is built for `linux/amd64` and `linux/arm64`. A `vX.Y.Z` tag publishes it and both workspace images as `X.Y.Z` and `latest`, and the tag must match `apps/server/package.json`. Pushes to `main` publish `main` and `sha-…` tags; the workspace images previously had only `sha-…` tags from manual runs, so the untagged references in the README pulled a `latest` that did not exist. Pull requests build the images on `linux/amd64` without publishing them. The README and docs pin images to `0.1.0`, and the docs describe the release steps.
- The landing page at `crumbli.ng` lives in `apps/site` instead of its own repository. Like `apps/docs`, it has its own lockfile outside the root Bun workspace. It now uses the Crumble green palette, the Crumble icon as its favicon, a screenshot of the web app, squircle corners, and a highlighted tagline. A Site workflow builds and type-checks it when `apps/site` changes.
- The documentation site at `docs.crumbli.ng` lives in `apps/docs` instead of its own folder. It's a Blume site with its own lockfile, outside the root Bun workspace, so the server's install and Docker image are unchanged. The docs are organized into Get started, Use Crumble, Web app, Self-hosting, Reference, and Contributing, use the Crumble green palette, and redirect the old Features and Architecture URLs. A Docs workflow checks and builds them when `apps/docs` changes.
- The web UI's code is grouped by feature. `apps/web/features/` has a folder per feature (bots, chat, group chats, activity, credentials, integrations, memory, schedules, settings, skills, jobs, and the bot desktop), `app/` holds the router and shell, `lib/` the API client and live streams, and `components/` the shared components. The UI is unchanged.
- Report why a bot desktop viewer did not open. The viewer's WebSocket closed with "The bot desktop is unavailable" whatever went wrong, and the server dropped the error, so a failure on Microsandbox could not be told apart from any other. Now the server logs the cause, and the WebSocket closes with code 1011 and a reason that names the failure: no desktop image, a bot without the desktop tool, a workspace that did not start, `desktop-start.sh` failing, the socat relay to its VNC server not starting, an unreachable workspace, or a server shutting down. The reason carries no guest output. Booting the machine when a viewer link is requested logs its failure too.
- Bot workspaces run as Effect services. `Workspaces` methods return Effects with tagged errors (`workspaces/workspace-errors.ts`) instead of promises: a boot fails with `WorkspaceBootFailed` naming the step that failed, `desktop-start.sh` with `DesktopStartFailed` and its output, a guest program stream with `WorkspaceStreamFailed`, and stops and syncs with `WorkspaceStopFailed` and `WorkspaceSyncFailed`. Opening a bot desktop on a server without a desktop image fails with `DesktopNotConfigured`, and for a bot without the desktop tool with `DesktopNotEnabled`, both before booting the machine. `MachineWorkspaces` serializes each bot's boots and stops with a semaphore, and neither stops halfway when its caller leaves; the Microsandbox and Railway backends boot in named Effect steps, and each resource a boot acquires is released if a later step fails. A Railway boot whose workspace proxy does not start now destroys the sandbox it created instead of leaving it running. `keepAwake` stays synchronous. The account's layer scope stops the workspaces it acquired (`acquireWorkspaces`), after the bot runtime as before, and the server's `workspaces` option is now such an acquisition. Pi's `ExecutionEnv` is unchanged: the pi-env connection runs the boot at that boundary. Idle stops and Railway's background checkpoints log a failure instead of dropping it. The API contract is unchanged.
- The server's features run as Effect services instead of classes over the store: `Bots` (formerly `CrumbleService`), `BotRuntime`, `BotMemory`, `BotMessaging`, `GroupChats` with `GroupTranscriptStore`, `BotSkills`, `SkillCurator`, `LearningReview`, `BotWorkspaces`, and `Plugins`, besides the credentials, providers, integrations, schedules, and push services converted before. Each feature registers its bot tools from a layer of its own. Closing an account interrupts waits for bot outcomes and background group turns between steps, and the next start recovers them as it recovers a crash; a step in progress, such as posting a group answer, still finishes. A `skill_manage` batch runs in one database transaction. Domain failures are tagged errors (`InvalidInput`, `Forbidden`, `NotFound`, `ReadOnly`, `Conflict`, `Gone`, `Unavailable`) mapped to the same HTTP statuses as before, and the Effect lint rules cover the whole server. Better Auth's users are read with Drizzle; SQL strings remain only in migrations and connection setup. The API contract is unchanged.
- Each account is built from one Effect `Layer` graph instead of hand-wired constructors and two cleanup lists: the data directory's lock, the database, credentials, workspaces, plugins, providers, MCP integrations, the bot runtime and chats, reviews, the curator, the scheduler, group chats, push, and the API, each released in reverse when the account closes or fails to start. Each feature registers the tools it offers bots in `BotExtensions`, at the position it had before, so the bot runtime no longer depends on every feature.
- The product database is read and written through Effect repositories with Drizzle queries instead of SQL strings, one per feature: agents, conversations, executions, memories, schedules, settings, secrets, agent and provider credentials, MCP servers, skills, learned changes, reviews, desktop control, and group chats. `ProductDatabase` and `SecretBox` (the account's encryption key) underlie them, and `productLayer` composes them on one connection. The synchronous `Store` facade moved to `apps/server/test/support/` for tests to set up and inspect an account.
- Push delivery runs as Effect services: `PushDatabase` (Drizzle on push.sqlite), `PushRepository` (devices, presence, and the outbox, with Drizzle queries instead of SQL strings), `PushTransports` (APNs and FCM; sends return typed failures, and configuration errors are a typed `PushConfigError`), `Push` (registration and delivery passes), and `PushDelivery`, a layer that delivers replies as they finish and polls for due retries. Each account runs push in a `ManagedRuntime` until the whole account is built from layers; a reply is written to the outbox without waiting for sends in progress, and closing stops polling and listening, writes replies still in memory to the outbox, makes one last delivery pass, and closes the database. Retry timing and expiry stay in the outbox. Tests control time with `TestClock`.
- Manage the product and push databases' schemas with Drizzle (`drizzle-orm` 1.0.0-rc.5 on `@effect/sql-sqlite-bun` 4.0.6). Each feature declares its tables in its own `schema.ts`, and drizzle-kit writes migrations to `apps/server/drizzle/`. The first migration is a baseline equal to the schema servers created until now: databases that already have it record it as applied, and older databases first get the column changes earlier servers made at startup. Tests compare the migrated schema with that of databases created by earlier servers. The Docker image now includes `apps/server/drizzle`.
- Replace deprecated APIs that type-aware linting reports: SQLite `exec` becomes its documented alias `run`, Zod string formats use `z.uuid()` and `z.iso.datetime()`, Bun WebSockets come from `@hono/bun` instead of `hono/bun`, and the web UI's route loaders use `queryClient.query` with `staleTime: "static"` instead of `ensureQueryData`. Adds the `@hono/bun` dependency. The API contract is unchanged.
- Run lint and type checks before each commit and the full check before each push, through Git hooks in `.githooks/` that `bun install` enables.
- Push delivery classifies send failures as typed errors (a rejected token, a terminal provider response, or a retryable failure) and owns its store, activity subscription, and outbox polling in an Effect scope; this is a bounded pilot of Effect 4.0.6. Closing push stops polling and listening, delivers what is queued, and then closes its store, which now happens even when that last delivery pass fails. A second close does nothing, and a failed background pass is logged instead of surfacing as an unhandled rejection. Retry timing and expiry stay in the outbox as before.
- Group the server's code by feature: `apps/server/src/` now has a folder per feature (`bots/`, `group-chats/`, `jobs/`, `workspaces/`, `bot-desktop/`, and others), plus `app/` for the server wiring, `contract/` for the API schemas, and `shared/` for domain types and the store. Tests sit next to the code they cover. The Docker image runs `apps/server/src/app/server.ts`.
- Type-check with every TypeScript strictness flag except `erasableSyntaxOnly` (shared in `tsconfig.base.json`), adding `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noUnusedLocals`, `noUnusedParameters`, `noUncheckedSideEffectImports`, and errors for unreachable code and unused labels. An optional property takes `undefined` only where its type says `| undefined`, and index signatures are read with brackets (`process.env["CRUMBLE_PORT"]`).
- Split the repository into Bun workspaces: the server, its tests, bundled skills, and the workspace image move to `apps/server`, and the web UI to `apps/web`, each with its own `package.json` and `tsconfig.json`. Scripts still run from the repository root, and the API and web UI are unchanged. The Docker image now runs `apps/server/src/server.ts` and reads bundled skills from `/app/apps/server/skills`; the legacy owner tool is `apps/server/tools/assign-legacy-owner.ts`, and the workspace image builds from `apps/server/workspace-image`.
- Compile the web UI with the project's own Tailwind (4.3.3) through `tools/tailwind-plugin.ts`, built on Tailwind's `@tailwindcss/node` and `@tailwindcss/oxide`. `bun-plugin-tailwind`, unchanged since October 2025, bundles Tailwind 4.1.14 and silently dropped newer utilities shadcn components use: the chat's scroll-to-bottom button lost its centering (`inset-s-1/2`) and sat under the sidebar, and the message scroller's `scrollbar-*` classes did nothing.
- Show a job's finished steps while it works. Coding and desktop job history hid every step of a running job, because it used the chat's rule for hiding the turn in progress, which the chat streams separately; now it hides only failed and aborted model calls. The web UI's job dialog reloads every 3 seconds while the job works.
- Let bots build a web app and test it ([0008](https://github.com/crumble-project/spec/blob/main/features/0008-web-app-testing.md)). Coding jobs start servers with `setsid` and a log file, so they keep running on `localhost` for later jobs; a server started with a plain `&` died at its next write, and one started with `nohup` alone when its command was stopped, on Railway and Microsandbox. Coding jobs run Playwright against the workspace's Chromium without downloading a browser (checked with Playwright 1.64.1 and Chromium 156 on both backends). Desktop jobs open those apps at their `localhost` URL, report each check as passed or failed, and say when a server is not running; the bot hands failures back to the coding job.
- Open the bot desktop viewer sooner, with a loading screen instead of a black page. The viewer connects once the VNC server listens instead of waiting for Chromium (`desktop-start.sh --display`); coding and desktop jobs still wait for the browser. Requesting a viewer link starts booting the bot's machine, and Railway boots write their guest files in parallel. On Railway a cold open took 10.7-14.9 s in four runs, against 13.8 s and 47.9 s before. Microsandbox gets the earlier connection once its desktop image is rebuilt with the new script.
- Open bot desktop viewer links without the owner's session again, as before multi-user accounts: a web view cannot send the session, so viewers got 401 and showed nothing. Tickets now name their account (`<account id>.<secret>`), and a request without a session goes to that account, which still checks the secret; it stays single-use. With a session, the link stays within the session's account, as before. noVNC's library files load without sign-in.
- Manage a bot's credentials in the web UI: a Credentials page, linked from the bot editor, lists requests and credentials in one table with their hosts, status, and last use. Requests are answered or declined there, credentials are added, edited, and deleted, and each one's uses are listed. A `request_credential` call shows in the chat as a card that opens the page, and the notice that follows is labelled with the credential. The tool's result now carries the request in its details. Adds shadcn's `table` and `dropdown-menu` components.
- Swap credential placeholders on Railway workspaces too. A guest program (`src/workspace-tunnel.py`) listens on `127.0.0.1:3128` in the sandbox and carries each connection over an exec stream to the server's workspace proxy, and coding jobs with credentials get `HTTPS_PROXY` pointing at it; a tool that ignores the variable connects directly and sends only the placeholder. Each boot installs the bot's authority in the sandbox.
