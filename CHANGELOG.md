# Changelog

## Unreleased

- Open the bot desktop viewer sooner, with a loading screen instead of a black page. The viewer connects once the VNC server listens instead of waiting for Chromium (`desktop-start.sh --display`); coding and desktop jobs still wait for the browser. Requesting a viewer link starts booting the bot's machine, and Railway boots write their guest files in parallel. On Railway a cold open took 10.7-14.9 s in four runs, against 13.8 s and 47.9 s before. Microsandbox gets the earlier connection once its desktop image is rebuilt with the new script.
- Open bot desktop viewer links without the owner's session again, as before multi-user accounts: a web view cannot send the session, so viewers got 401 and showed nothing. Tickets now name their account (`<account id>.<secret>`), and a request without a session goes to that account, which still checks the secret; it stays single-use. With a session, the link stays within the session's account, as before. noVNC's library files load without sign-in.
- Manage a bot's credentials in the web UI: a Credentials page, linked from the bot editor, lists requests and credentials in one table with their hosts, status, and last use. Requests are answered or declined there, credentials are added, edited, and deleted, and each one's uses are listed. A `request_credential` call shows in the chat as a card that opens the page, and the notice that follows is labelled with the credential. The tool's result now carries the request in its details. Adds shadcn's `table` and `dropdown-menu` components.
- Swap credential placeholders on Railway workspaces too. A guest program (`src/workspace-tunnel.py`) listens on `127.0.0.1:3128` in the sandbox and carries each connection over an exec stream to the server's workspace proxy, and coding jobs with credentials get `HTTPS_PROXY` pointing at it; a tool that ignores the variable connects directly and sends only the placeholder. Each boot installs the bot's authority in the sandbox. Bot desktops on both backends add it to Chromium's certificate store at startup, which needs `libnss3-tools`: publish a new workspace desktop image before deploying.
- Swap credential placeholders for their values on Microsandbox workspaces ([ADR 0006](docs/adr/0006-credential-proxy.md)). The workspace proxy hands TLS connections to a bot's credential hosts to a credential proxy, which presents a certificate from the bot's own authority, replaces the placeholder in headers, HTTP Basic credentials, and the query string, and sends the request on over verified TLS to public addresses only. Values are scrubbed from responses, and every use is recorded. Each boot installs the bot's authority in the guest, and coding jobs with credentials get `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, and `NODE_USE_ENV_PROXY`. Adds the `pkijs` and `asn1js` dependencies.
- Give bots credentials without putting values in their workspace ([feature 0007](https://github.com/crumble-project/spec/blob/main/features/0007-credentials.md)), first part. A bot with coding jobs asks for one with the new `request_credential` model tool (name, hosts, reason), and the owner saves the value through `PUT /v1/agents/{id}/credentials/{name}`, which starts a bot turn with a notice from origin `credential`; deleting a request declines it the same way. `GET /v1/agents/{id}/credentials` lists credentials and pending requests without values, and `GET /v1/agents/{id}/credentials/{name}/uses` lists the last 90 days of uses. Values are encrypted with the server's key. Every command a coding job runs sees each credential as an environment variable holding a placeholder, and the job's instructions list them. The credential proxy that swaps placeholders for values is not built yet, so the placeholders do not authenticate anything. Contract 3.1.0.
- Check contract compatibility with oasdiff 1.34.1, locally and in CI.
- Run workspaces in Railway sandboxes with `CRUMBLE_WORKSPACE_BACKEND=railway` ([ADR 0005](docs/adr/0005-railway-workspaces.md)), so coding jobs need no `/dev/kvm` and the server can run on Railway. - Review tool-heavy turns in the background so bots learn from their work ([feature 0005](https://github.com/crumble-project/spec/blob/main/features/0005-learned-skills.md)). After a bot chat turn settles, its tool-activity rounds count towards two per-bot counters; when the skill counter reaches its threshold (default 10 rounds since the bot last wrote a skill), or the memory counter its own, a review runs in a separate conversation on the bot's `reviewModel`, or its own model, with only the skill and memory tools. It reads a bounded digest of the turn, patches or creates skills in the preference order Hermes Agent uses, never deletes one, and skips environment failures, one-off tasks, and dead ends. Scheduled tasks and group turns are not reviewed; a review interrupted by a restart is dropped. The review reads the turn in full, with the chat before it for context and the bot's standing instructions, and its whole input, across every request it makes, is capped at 75% of the review model's context window, at most 600,000 tokens, or the lower `maxInputTokens` in the new `review` agent settings, which also hold the thresholds and an off switch. A turn that writes a skill or memory restarts that store's count, so only the rounds after the write count. What a review changed is announced as a `learned` activity event and kept in `GET /v1/agents/{id}/reviews`, so clients can show a notice in the bot chat, also after reconnecting.
- Curate bot-created skills: one unused for 14 days becomes stale and one unused for 30 days is archived and leaves the bot's skill list, every six hours and on startup. Pinned skills and skills a scheduled task names are left alone; nothing is deleted. Loading a stale skill makes it active again, and the owner restores or pins a skill through `PATCH /v1/agents/{id}/skills/{skillId}`.
- Let bots write their own skills with the new `skill_manage` model tool ([feature 0005](https://github.com/crumble-project/spec/blob/main/features/0005-learned-skills.md)): create, patch, rewrite, and delete a skill and write or remove its reference documents, as one atomic batch. A bot must load a skill in the same turn before changing it; shared and default skills are read-only and a bot shadows one by creating its own skill of the same name. The tool validates names, sizes, and document paths, and returns advisory findings for missing descriptions, oversized bodies, incident-log shape, and document sprawl. Bots are told to put procedures, pitfalls, and the owner's corrections for a kind of work into skills and keep memory for facts that hold in every conversation.
- Record every skill and memory change by the owner, a bot, or a review, with the state before and after and the execution it came from, in `GET /v1/changes`. `POST /v1/changes/{id}/revert` restores the state before one change and records the revert.
- Make skills packages that bots load on demand ([feature 0005](https://github.com/crumble-project/spec/blob/main/features/0005-learned-skills.md)). A skill has a name, a one-line description, instructions, and up to 20 reference documents under `references/`. A bot's instructions now list its skills by name and description instead of inlining every body; the new `skill` model tool lists them and loads one skill or one document, and loading counts as using it. A bot's own skill shadows a shared skill of the same name, which shadows a default. Default skills in the skills directory may add reference documents as `references/*.md`. A bot's own skills move out of the agent row into the skill library on startup; the agent's inline `skills` field keeps reading and writing them by name, so a kept skill keeps its description, documents, provenance, and usage. Skill records carry who created them, the execution they were learned from, usage counts, a lifecycle state, and a pin for the learning loop that follows.

## Contract 3.1.0

- Add credentials a bot's coding jobs use without seeing their values: `GET /v1/agents/{id}/credentials` lists the bot's `Credential`s and pending `CredentialRequest`s, `PUT /v1/agents/{id}/credentials/{name}` creates or updates one (`hosts`, and a write-only `value`) and answers a request of the same name, `DELETE /v1/agents/{id}/credentials/{name}` deletes one or declines a request, and `GET /v1/agents/{id}/credentials/{name}/uses` pages its `CredentialUse`s from the last 90 days. Values never appear in responses.
- Add the `request_credential` model tool. Its tool result carries the request (`name`, `hosts`, `reason`, `requestedAt`) in `toolDetails`, and answering or declining posts a message with origin kind `credential` and the credential's name.

## Contract 3.0.0

- Replace the shared server bearer token with Better Auth account sessions. Clients must sign in through `POST /api/auth/sign-in/email` and use the returned session token, or use the browser session cookie. Legacy server tokens are rejected.
- Scope `/v1` resources, event streams, and desktop viewers to the signed-in account. Shared memories and skills belong to that account's bots. Cookie-authenticated writes require the configured `Origin`.
- Add the `SessionCookie` authentication alternative to the OpenAPI document and describe `BearerAuth` as an account session token. Existing native clients need account sign-in support before upgrading.

Clients that decode `activities` as `OperationalActivity` only must handle the new item.
