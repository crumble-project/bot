# Implicit state machines

This inventory maps temporal protocols in the Crumble server and web app at commit `d5de813`.
It identifies states, transition triggers, and recovery boundaries. It is not a defect report.

## Scope and interpretation

Scope: `apps/server/src`, `apps/web`, and interactive behavior in `apps/site` within this repository.
Native Apple and Android clients, sibling repositories, dependencies, generated code, and historical migrations are outside scope.
All server feature directories were assigned to the audit. Coverage varies by directory; this is a source-level inventory, not a completeness proof.

A state machine exists when the meaning of an event depends on what happened before it.
Its state can live in database rows, resource ownership, promises, maps, timers, callbacks, or React effects.
The state names in this document are conceptual unless formatted as literal code values.

Classification:

- **Implicit:** State and transition rules emerge from fields, collections, and control flow.
- **Mixed:** Named statuses exist, but additional lifecycle phases and guards remain distributed.
- **Explicit:** The code already centralizes a transition model or uses a discriminated protocol union. These are identified separately.

A status enum alone does not describe a complete machine. A state machine is not inherently technical debt.
Routine CRUD, isolated loading spinners, and pure data transformations are not separate entries.
Related submachines are grouped when they share ownership and recovery rules.

Source references use `path:line`; line numbers refer to the audited commit. Server paths are relative to `apps/server/src/`.
Web and site paths are relative to their respective application directories.

## Highest-value boundaries to make explicit

These priorities reflect cross-service coordination and recovery complexity, not demonstrated bugs.
Effort estimates are relative: medium spans a few implementation units; large spans services or persistence boundaries.

| Priority | Boundary | Why it matters | Incremental next step | Relative effort |
| --- | --- | --- | --- | --- |
| 1 | Bot input admission, cancellation, and publication: R01–R04, W01–W03 | Product rows, durable runtime state, SSE snapshots, and optimistic delivery encode different milestones. | Document the shared protocol and invariants. Test duplicate submission, ambiguous HTTP failure, cancellation, and reconnect sequences before changing representation. | Large |
| 2 | Jobs, questions, and delegation: J01–J04, R11–R12 | Durable phases interact with stop generations, exclusive ownership, question races, and composite completion. | Keep the existing reporter union. Name invariants around holder ownership, stop generation, question identity, and open turn work. Test transition sequences across recovery. | Large |
| 3 | Desktop authority and observation safety: J10–J14, W09–W10 | Owner control, approval, observation freshness, and password exposure are independent safety dimensions. | Model these dimensions separately. Make dispatch guards explicit without flattening them into one enormous status enum. | Large |
| 4 | Workspace recovery and checkpoints: J06–J09 | Resource lifetime and persisted recovery differ across Microsandbox and Railway. | Specify shared lifecycle invariants and provider-specific recovery contracts. Test teardown/readiness and checkpoint/stop races. | Large |
| 5 | Gateway receipt delivery: I05–I07 | A pending receipt hides execution waiting, partial external delivery, rate limits, and reconnect ownership. | Derive named receipt phases from persisted fields; centralize guards for the next admissible action. Test partial sends across restart. | Medium to large |
| 6 | Group turn publication: R06–R10 | Pending versions, cursors, budgets, and posting records protect several independent invariants. | Describe queue admission and publication as separate protocols. Test owner posts during startup and recoverable publication failure. | Medium to large |
| 7 | Automation admission versus completion: I01–I03 | Advancing a schedule or marking an event dispatched means durable admission, not finished work. | Preserve this distinction in names and tests. Cover refused admission, retry, overlapping ticks, and restart. | Medium |
| 8 | Secret cache and invalidation: J15–J18 | Freshness, allowed stale fallback, revocation, and late refresh completion have security-sensitive differences. | Centralize freshness decisions and invalidation invariants. Test refresh/disconnect races and disallowed stale fallback. | Medium |

A staged approach avoids a repository-wide rewrite:

1. Capture the invariants and transition-sequence tests for the first three boundaries.
2. Extract pure transition decisions where distributed guards are hardest to reason about.
3. Apply the same pattern to gateway, group, automation, and cache boundaries as those features change.

Do not replace every boolean with a state-machine framework.
Keep existing explicit unions where they work. Favor named states and guarded transitions at ownership and recovery boundaries.

## Audit limits

This inventory contains 92 grouped implicit or mixed protocols, plus notes on already-explicit models.
Grouping is architectural judgment: several rows contain smaller request, parser, or resource-lifetime machines.
It is not a claim that exactly 92 automata exist in the codebase.

The audit read relevant implementations and screened feature directories for temporal state.
It did not exhaustively read every API wrapper, tool facade, schema, or pure helper.
Routine CRUD editors, filters, disclosures, selectors, and loading/error states are collapsed rather than listed individually.
Third-party Pi Durable, pi-env, Better Auth, WebAuthn, Discord, MCP, noVNC, and transport internals are excluded.

Representative admission, group publication, gateway delivery, workspace, job, held-action, secret-cache, invite, encryption-key, reconnect, and optimistic-delivery code was cross-checked during synthesis.
No tests, browser scenarios, fault injection, or controlled mutations were run. No runtime defects are established by this inventory.
Only this report was added; application code was not changed.
