# Logins implementation plan

> Implement one task at a time. Review each deliverable before starting the next. Steps use `- [ ]`.

**Goal:** Desktop jobs sign in to websites with logins the owner stores per bot (#63), and bots ask the owner for a missing login (#64), without a login value ever reaching a model or transcript.

**Architecture:** A `logins` module mirrors `credentials`: tables, a repository, an Effect service with a promise-style access object, HTTP routes, and a web settings page. Each field (username, password, one-time code secret) is a `secretSource` read through `SecretValues`. The `computer_use` tool gets a `fill_login` action that checks the active Chromium tab's URL through cua-driver's browser binding and types the value with `browser_type` into that exact tab, so the value goes from the server to the page and nowhere else.

**Depends on:** `docs/plans/2026-10-29-browser-actions.md` Tasks 1, 3 and 4 (arguments on stdin, page binding, page refs).

**Source:** GitHub issues crumble-project/bot#63 and crumble-project/bot#64 (parent #61). Spike run on 2026-10-29 in the local Microsandbox desktop VM (`crumble-workspace-desktop:dev`, cua-driver 0.38.0); findings under Decisions.

## Decisions

Spike findings (verified in the VM):

- The accessibility tree from `get_window_state` carries no page URL. The address bar entry shows typed text before return (`bank.example.com` typed, not loaded), so it must never be the host check.
- `cua-driver call get_browser_state {session, pid, window_id}` (bind mode) returns `{ target_id, tabs: [{ tab_id, url, title, active }] }`; the active tab's `url` is exact. Before the first bind after each Chromium start it refuses with `refusal.code: "browser_consent_required"`; `browser_prepare {session, pid, window_id, strategy: {kind: "existing_profile"}}` then attaches. Preparing opens a setup page, foregrounds the window, focuses the address bar, and clicks Chromium's consent dialog itself (`side_effects` in its reply). The image already starts `cua-driver serve --grant existing-profile` (`workspace-image/desktop/desktop-start.sh:24`).
- `get_browser_state {session, target_id, tab_id, snapshot_format: "semantic_v2"}` lists form fields under `refs` (not `content_refs`) as `{ ref: "p<n>:<i>", role: "textbox", name, states: { focused?: true, editable } }`. A field the job clicked shows `states.focused: true`. Field values are `null`; a password field is masked.
- `browser_type {session, target_id, tab_id, ref, text, replace: true}` typed into the password field (`summary: "typed 16 char(s) ..."`, `effect: "unverifiable"`, no value echoed). Refs are invalidated by navigation, so a page that changes between check and type refuses instead of receiving the value.
- After typing, the value appeared in neither the semantic snapshot nor the accessibility capture.
- Chromium showed a "Save your password" button after the fill. Its password manager would store the login in the profile on `/workspace`, where coding jobs can read it.
- After `browser_prepare`, Chromium listens for remote debugging on `127.0.0.1:9222`. Another process connecting gets Chromium's "Allow remote debugging?" dialog on the desktop and waits. Each Chromium restart needs a new `browser_prepare`.

Design:

- `fill_login` is a `computer_use` action, not a separate tool: it shares the job's cua-driver session, control gate, window targeting, and the page binding of its latest read. Arguments: `login` (name), `field` (`username` | `password` | `one_time_code`), `ref` (the field's page ref from the job's latest `read` of the active tab). The issue's `element_token` became `ref`, matching page actions.
- The ref's role and frame come from the job's latest `read`, which `computer-use-page.ts` keeps in `state.lastRead = { page, read }` with the tab binding it came from; no extra call. `fill_login` types through that binding and checks the host of `read.page.url`: a ref is valid only while its page hasn't navigated (cua-driver refuses it as `browser_ref_stale`), so that URL is the URL of the page the ref belongs to. It must be an editable `textbox` with `frame: "main"`. A ref not in the latest read refuses ("read the page, then fill_login with a ref from it"); a ref in another frame refuses ("fill_login fills fields of the page itself, not of embedded frames"): cua-driver can type into cross-origin iframes, and whether it reports a frame's origin is unverified (`docs/bot-desktop-research.md`).
- The host check requires `https:` and `hostMatches(login.hosts, url.hostname)` (`src/shared/domain.ts:372`). Login hosts use `credentialHosts` (public DNS names, `*.` wildcards).
- `fill_login` never binds: binding again would supersede the read's refs. Without a latest read it refuses: "read the sign-in page, then fill_login with a ref from it".
- The value reaches cua-driver only through the exec's `env` and stdin (browser actions plan Task 1); it is never written to the guest disk or a command line.
- Login values never appear in tool output: `fill_login` replies `filled <field> of login <name> on <host>`, and every later text result of that job's `computer_use` (captures, reads, step results) has each value it filled replaced with `[login <name> <field>]`. `read` already hides password field values (browser actions plan).
- One-time codes: a code stored in Crumble or read from Bitwarden is a TOTP secret (base32, or an `otpauth://totp/` URI whose `secret`, `digits`, `period`, `algorithm` are honored; defaults SHA-1, 6, 30). Codes are computed with `node:crypto` HMAC (RFC 6238); no new dependency.
- 1Password: the owner gives one item reference `op://<vault>/<item>`; fields read `op://<vault>/<item>/username`, `.../password`, and `.../one-time password?attribute=totp` (a computed code, used as is). Bitwarden: one secret ID per field. A field can also be stored in Crumble. Each field picks its own source, except that a 1Password item reference fills all fields of that login.
- Login names: `loginName`, 1-64 of `[a-z0-9._-]`, starting with a letter or digit (`github`, `acme-portal`). Not environment variables, unlike credential names.
- Every fill attempt that reached the value read is logged in `login_uses`: `at`, `host`, `field`, nullable `error` (why the value couldn't be read). A refusal before reading (wrong host, unknown login, bad ref) is not a use. Retention is 90 days, as for credential uses.
- A filled login's value enters the workspace (the page holds it), unlike a credential's. The glossary's **Credential** entry stays as is; **Login** says so explicitly.
- Chromium's own password saving is turned off by a managed policy in the desktop image: `/etc/chromium/policies/managed/crumble.json` with `{"PasswordManagerEnabled": false}`.
- 1Password Agentic Autofill is dropped: it needs a 1Password account and the extension in the desktop to spike, and the fill tool ships alone (#63 allows this).
- #64 requests mirror credential requests: `login_requests` keyed by bot and name, one open request each; `request_login` is a direct model tool (`callers: ["model"]`) whose result `details` carries the request so clients render the card.
- When no login matches the page's host, `fill_login` refuses with: "No login of this bot covers <host>. Say so in your answer, naming <host>, so the bot can ask the owner for a login." The desktop job does not get `request_login`.
- Contract: version 3.4.0 has no `contract-v3.4.0` tag yet, so these changes join the `## Contract 3.4.0` changelog section and the version stays 3.4.0 (`src/contract/api-contract.ts:1076`).

## Constraints

- Read `apps/server/node_modules/effect/AGENTS.md` before writing Effect code (`bot/AGENTS.md`).
- Product language follows `GLOSSARY.md`: **Login**, **Credential**, **Password manager**, **Desktop job**. UI copy says "login", never "account", "password entry", or "secret".
- Write-only: login values never appear in a response, log line, tool result, or notice.
- Tests use the fake vendor (`test/support/fake-password-manager.ts`) and the scripted guest (`test/fixtures/scripted-guest.ts`); never a real password manager, network, or VM in default tests. VM tests run only with `CRUMBLE_VM_TESTS=1`, locally.
- Web editing opens in `EditorSheet`, never a modal. Settings rows are one line: logo or icon, name, action; no status lines.
- Migrations: `bun run db:generate` from `apps/server` after changing `schema.ts` (drizzle store config).
- Contract changes: `bun run openapi:generate` from `bot/`; `CHANGELOG.md` gets lines under `## Unreleased` and `## Contract 3.4.0`.
- Check command, from `bot/`: `bun run check`. CI unit tests stay under two minutes. After changing `apps/docs`, run `bun run check` from `apps/docs`.

## Out of scope

- 1Password Agentic Autofill, passkeys, filling during taking control.
- Apple and Android UI; new response fields stay additive.
- Filling into non-Chromium windows or non-https pages.
- Desktop jobs requesting logins themselves.
- Publishing a new desktop image tag; the policy file ships in the Dockerfile and reaches users with the next `workspace-image-v*` release.

## Review focus

1. The page navigates to another host between the host check and `browser_type`: the type must refuse (stale ref) and nothing be typed. Test in Task 4 with a scripted `browser_type` refusal.
2. A filled username that the page echoes ("Signed in as ada@example.com") shows up in a later capture: it must be replaced with `[login <name> username]`. Test in Task 4.
3. The owner holds control when `fill_login` is called: it waits like every action and then refuses as stale, never typing into a page the owner changed. Test in Task 4.
4. A login switches a field from a 1Password reference to a value: the old reference is forgotten (`SecretValues.forget`) and the password manager's `usedBy` no longer lists it. Test in Task 1.
5. A request answered by saving a login with a different name than requested: the request stays open. Test in Task 7.
